# 🏺 Database Migrations with Alembic

This workspace uses **Alembic** alongside **SQLAlchemy 2.0** to handle schema migrations for our **MySQL** database. This file documents the architecture, setup workflows, and day-to-day command pipelines.

---

## 🏗️ Migration Architecture

Our migration setup is decoupled and integrated directly into our code layout:

```text
apps/api/
├── src/
│   ├── migrations/          # Controlled entirely by Alembic
│   │   ├── versions/        # Chronological storage for database revisions
│   │   └── env.py           # Core orchestration engine (reads Pydantic Settings)
│   ├── config.py            # Loads configuration dynamically from environment
│   ├── database.py          # Session engines and Declarative Base declarations
│   └── user/
│       └── models.py        # SQLAlchemy source-of-truth database entities
├── .env                     # Contains sensitive local DATABASE_URL keys
└── alembic.ini              # Main execution configuration file
```

---

## ⚙️ How it Works under the Hood

1. **No Hardcoded Secrets**: `alembic.ini` leaves the connection string blank. When you trigger a command, `src/migrations/env.py` dynamically boots up our Pydantic `Settings` singleton to read the `DATABASE_URL` safely from `.env`.
2. **Metadata Introspection**: Our `env.py` imports `Base` from `src/database.py` and targets your feature models (e.g., `from src.user.models import User`). This lets Alembic compare your local Python files to your live database columns.

## 🚀 Common Commands

Always run these commands from the **`apps/api/`** workspace with your virtual environment (`.venv`) active.

### 1. Generating Migrations (When you change models)
Whenever you create a new table, add a column, or drop a field inside a `models.py` file, execute an autogenerated revision script:
```bash
alembic revision --autogenerate -m "describe_your_changes"
```
*Always inspect the newly generated file inside `src/migrations/versions/` before running it to confirm it captured your changes correctly.*

### 2. Applying Migrations (Upgrading)
To execute pending migration steps and bring your active database completely up to speed with the latest schema models:
```bash
alembic upgrade head
```

To move your schema forward by exactly one incremental step:
```bash
alembic upgrade +1
```

### 3. Reverting Changes (Rolling Back)
If something breaks or you want to undo the very last migration applied to your database:
```bash
alembic downgrade -1
```

To completely wipe all custom structural database tables back to a blank slate:
```bash
alembic downgrade base
```

### 4. Diagnostic Commands
To check what migration revision checkpoint your database is currently occupying:
```bash
alembic current
```

To view a chronological history log of all migrations tracking across this codebase:
```bash
alembic history --verbose
```

## ⚠️ Important Rules & Best Practices

*   **Never Modify Applied Versions**: Once a migration file inside `versions/` has been pushed or committed to git, **never edit it**. If you need to make changes, generate a brand new revision step.
*   **Import New Models**: When creating a completely new feature folder (e.g., `src/students/models.py`), you must explicitly import that new model inside **`src/migrations/env.py`**. If you forget to import it, Alembic won't be able to see it and won't autogenerate the migration paths.
*   **Keep `.env` Out of Source Control**: Never commit your `.env` file to Git. Use `.env.example` to distribute structural updates across your engineering environments safely.
